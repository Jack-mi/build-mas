# codexwright 商业化改造方案

方案日期：2026-11-09。状态：方案讨论，未实施收费、远程服务或多租户部署。

## 1. 决策与范围

商业化出售的是工作流工程能力与托管执行服务，MCP 是交付接口，Skill 是调用指引。移除 builder CLI 不影响商业化，也不意味着 MCP 必须包装其他命令。

本轮已确认的产品方向：

- 一个 `BuildService` 核心，由 MCP 工具直接调用；不重新实现一套业务逻辑。
- builder 面向用户的入口收敛为 **Skill + MCP**，不增加 Hook。
- 移除 builder CLI 命令、分发及命令行备用流程；首次注册、导入、登录、恢复和审批不能因此断掉。
- 保留生成目标工作流自己的 library、CLI、task-level MCP；删除范围不扩展到 target CLI、受控工具执行或 Codex SDK 必需的运行时。
- 商业化本次只梳理方案，不新增鉴权、支付、计费、远程执行代码，不安装新依赖，不提交、推送或部署。

方法取舍采用《简约至上》的“删除策略”：删重复入口和操作负担，保留核心能力、安全、用户控制与错误恢复。架构依据为本轮已核对的 [agents-best-practices](https://github.com/DenisSergeevitch/agents-best-practices/tree/da245f8cbfc4c358e8c3cde61dbb703bd40292bc)，仅复用权限、记录来源、累计预算与未知结果对账原则，不引入新 Agent runtime。

## 2. 现状、迁移目标与商业化目标

### 2.1 已有基线

截至方案编写时，`0.2.0` 已有本地 stdio MCP、共享核心、私有工作区与暂存提案、精确审批、验证和失败记录。相关来源为 [README](../README.md)、[产品定位](product-positioning.md)、[MCP 实现](../src/codexwright/mcp_server.py)、[业务核心](../src/codexwright/service.py)、[状态存储](../src/codexwright/store.py) 和 [运行时边界](../src/codexwright/runtime.py)。这些文件会随主线程迁移更新，应以对应提交及验收记录为准。

当前商业能力的缺口：

| 边界 | 当前基线 | 商业化需要补齐，尚未实现 |
| --- | --- | --- |
| 交付 | 本地 stdio；以本机项目路径登记工作区 | HTTPS MCP 与上传/授权导入的云端工作区 |
| 身份 | 本机 runtime 账号与配置；不是 SaaS 租户身份 | 服务账号、OAuth、租户及角色权限 |
| 计费 | 没有套餐、余额、报价或支付账本 | 权益、预算预留、结算、退款及对账 |
| 执行 | 已有本地执行限制；验收范围以记录为准 | 云端租户沙箱、网络和凭据隔离、资源限额 |
| 数据 | 本地私有记录；保留策略仍为人工管理 | 可执行的保留、删除、导出和事故处理规则 |
| 授权 | 当前项目尚未选择许可证 | 源码、依赖、Skill、模型及用户代码的商用授权核验 |

本地 stdio 能启动、已有 macOS 验收或成功模型调用，都不证明 SaaS 已上线、Linux 多租户安全通过或收费可投产。当前本地状态锁也不是跨节点的余额事务系统。

### 2.2 主线程的 0.3.0 迁移目标

主线程正在实施移除 CLI，以下是该次迁移的接口目标，**不是本方案宣告已验收**：

- 用 `python -m codexwright.mcp_server` 直接启动 stdio；home、model、allow-apply 由环境配置选择，不提供 builder 命令行操作。
- MCP 补充 `codexwright_register`、`codexwright_import`、`codexwright_recover`、`codexwright_login`，保留 preflight、invoke、verify、status、read 及按策略启用的 apply。
- Skill、各宿主 launcher、插件配置、安装输出、文档与测试不再依赖 builder CLI。
- 不支持人类确认的客户端必须返回可解释的阻塞，不能退回已删除的 CLI，也不能把模型传入的批准字段当作人类审批。

登录 runtime 账号与登录商业服务是两件事。未来云端用户只授权商业服务账号，不会获得运营方模型账号或 API Key。Codex Python SDK 的本地 app-server/固定运行时依赖仍按 [官方 SDK 文档](https://learn.chatgpt.com/docs/codex-sdk) 管理，删除自有 CLI 不删除依赖运行时。

### 2.3 商业目标形态

```text
用户当前 Coding Agent
  └─ Skill 指导调用，不执行收费或批准
       └─ HTTPS MCP edge：认证、参数与权益检查、任务接收
            ├─ 服务端账本：报价、预留、结算、对账
            └─ 租户 sandbox worker
                 └─ 同一个 BuildService → Codex SDK
                      └─ 提案、验证证据、任务及用量凭据
```

edge 只做传输与商业控制的薄适配，业务核心不依赖支付厂商，不能复制工作流逻辑；worker 不处理信用卡、支付密钥或账本管理权限。Skill 不提供可信授权，移除或篡改 Skill 也不能绕过服务端检查。本地代码中的付费开关不能作为云端权益保护的安全边界。

## 3. 最小收费模型

建议从一种任务计费方式开始，不同时上线按工具、按 Token、按时长和复杂套餐。需求与付费意愿尚未实测，以下是待验证建议，不是价格表或营收预测。

| 能力 | 建议对外计价 | 必须保留的规则 |
| --- | --- | --- |
| preflight、注册、导入 | 免费接入；导入有大小、次数及容量上限 | 仍认证、校验材料和限流；不允许无限存储 |
| `status`、`read`、用量/结算查询 | 免费 | 按租户授权、分页与限流；不因套餐到期阻挡应保留的账单争议证据 |
| `analyze`、`review`、`explain`、`plan` | 少量体验额度，之后按任务扣额度 | 它们可能调用模型，并非零成本；免费额度也须原子预留 |
| `build`、`edit`、`diagnose`、`migrate`、`refactor` | 按已确认的 operation 与任务扣额度 | 明确输入规模、执行预算和交付物，不按 Agent 数量计费 |
| `verify` | 任务内约定次数；额外深度验证单独报价 | 候选验证、应用后验证、再次执行分别展示，防止重复收取已包含费用 |
| `apply`、`recover` | 同一任务范围内不另收操作费 | apply 仍需独立写入审批；recover 对账/取回已有结果免费，新增计算另报价 |

`codexwright_invoke` 内多个 operation 共用一个工具，不必为价目表复制十几个 MCP 工具。`auto` 必须先确定实际 operation 与计费范围，再报价执行；若后续转成更昂贵操作、变更材料或突破授权预算，暂停重新报价，不静默升级。报价前若必须调用模型判别，应使用明确的小额免费预算，不先运行完整付费任务。

**计费单位是一次逻辑任务，不是一次 MCP 请求。** 提交后的 `status/read` 轮询、断线重连、重复投递、读取大 diff 的分页都不重复收费。相同会话中的实质新需求是新任务，必须明确区分，不能把会话做成无限消耗的授权。

对用户先提供固定任务额度与上限，内部记录模型输入/输出/缓存用量、worker 资源和验证成本，覆盖子运行与重试。不能只统计最后回复长度。成本数据用于验证毛利，不自动变成对用户的账单；具体币种、额度单位、税费和定价由用户确认。

## 4. 商业控制面与 MCP 协议

采用 [MCP 2026-07-28 HTTP 授权规范](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization)，以 HTTPS MCP 为资源服务器、OAuth 为用户授权渠道。实现时核对实际 SDK、协议版本与宿主兼容性，不把新规范字段直接套进本地固定版本。HTTP 授权与本地 stdio 从环境取得凭据的机制分开处理。

最小控制面需要以下能力，不要求全部变成独立 MCP 工具：

- 获取当前用户权益和任务预算，读取服务端报价、确认范围与结算记录。
- 校验真实人类确认或已签署的有限消费授权，预留额度后接收一次任务。
- 使用现有 invoke/status/read 协议接续结果；商业报价和状态作为结构化扩展，不由模型生成权威价格。
- 新增单独报价工具仅在宿主交互确实需要时采用；不提供任意执行命令的通用工具。

[MCP tools 规范](https://modelcontextprotocol.io/specification/2026-07-28/server/tools) 允许工具列表按请求授权变化，顺序应稳定，不能按连接状态随意漂移。建议保留精简稳定工具面，具体 operation 的权益在调用时检查。隐藏付费工具不是安全保障，缓存过的工具名或直接 `tools/call` 仍必须经过权限、预算和租户检查。

MCP 身份、商业套餐、可读项目范围、消费批准、代码写入批准互相独立。OAuth token 通过不代表某个 operation 已付费，也不代表可以执行用户代码或覆盖项目文件。

## 5. quote → reserve → execute → settle

以下是拟定状态机，不是当前接口返回值；不能把商业状态覆盖现有运行与验证状态。

```text
quoted → awaiting_confirmation → reserved → executing → settling → settled
   └─ expired/rejected              └─ 未启动且确认无效果 → released
                                  executing/settling → outcome_unknown
                                      └─ reconcile → settling 或 released
```

### 5.1 报价与绑定

报价由服务端生成并保存，至少绑定：

- `tenant_id`、用户/付费账号、`workspace_id`、`session_id`、逻辑 `task_id`。
- 规范化请求 hash、已选 operation、材料清单及 hash、工作区 snapshot/revision。
- 架构/策略/工具 schema 与价目版本、计费单位、最高扣费、报价有效期。
- 模型/验证预算、包含重试次数及验证范围、失败/取消规则、确认凭据。

租户与用户身份来自可信认证上下文，不接受模型字段覆盖。报价、审批和结算记录均由服务端签发引用，客户端不能自行生成。一份消费许可只对其精确任务和预算有效；提案写入许可另外绑定 proposal hash、目标版本与作用范围，两种许可不可互用。

高成本操作暂停等待明确人类确认，详情必须包含范围、上限、费用单位、取消及失败规则。依据 [RICH 显性确认](https://github.com/ant-design/x/blob/8b76d6a22067945c5d224c02ee1448dfb30144ff/packages/x/docs/spec/confirm.zh-CN.md)，这里只采用高成本与明确授权原则，不要求 Ant Design X 界面。明确、有限的既有授权可减少重复确认，不能把一句“继续”变成不限额度授权。无法证明确认来源时停在等待确认。

### 5.2 预留与并发

在账户/租户账本事务内，检查权益、价目/报价版本、余额和消费授权，原子创建 reservation 与 accepted task；再通过可恢复的任务投递记录派发 worker。接受凭据不代表已完成。

额度守恒按授予、调整、最终消耗和有效预留共同核算：`available = grants + adjustments - settled_consumption - active_reservations`，不得为负；现金收款账、服务额度账与模型成本账分别记录，不把一次预留当作已收款。跨会话、节点、worker 和人工操作都共享同一余额事务边界。

幂等键以 `(tenant_id, logical_task_key)` 唯一约束，并绑定请求 hash；同键同请求返回原任务，不再预留或运行，同键不同请求返回冲突。派发/恢复采用任务租约与 fencing token，旧 worker 不得晚到提交第二份结果或结算。服务端重试仍计入原预算，不能通过换 run ID 绕过最高消费。

### 5.3 执行与结算

- worker 只执行账本已授权的任务版本；执行前和 apply 前重新校验租户、权限、预算与目标状态。
- 固定额度按已披露交付条件结算；若以后采用实际用量计价，实际扣费不得超过已确认上限。余量释放与最终扣额在同一事务完成。
- `settled` 表示任务费用结算完成，不表示服务已经从支付平台收齐款；`completed` 也不表示验证 `passed`。
- 完成记录附逻辑任务、运行/提案及材料版本、验证覆盖、价格版本、计量证据、预留/实扣/返还额度和结算引用。
- 计费汇报失败只重试汇报，结果读取失败只重试读取，都不重启模型或重新应用提案。

### 5.4 unknown 与对账

连接断开、观察超时、worker 租约过期、支付 API 超时或应用结果未收到，都不足以判定失败或无副作用。保持 `outcome_unknown`，**冻结对应预留，不自动扣成最终账单、不因 TTL 自动释放、不换幂等键重跑**。

对账根据 worker/runtime handle、运行回执、提案/目标 snapshot、账本及支付对象查明结果。只有证据证明未执行且无效果才释放；证明完成则按原报价结算；证明部分执行则依据已披露规则处理。缺证据时继续冻结并进入人工处理队列，提供用户可查询状态及客服升级途径；不能无限静默冻结或凭模型判断解冻。冻结期间不继续后台消耗预算，停止新工作必须有执行器确认。

## 6. 支付、失败和退款规则

建议先做既有账号额度/订阅权益，再决定支付厂商；Stripe 仅为候选。自有任务账本负责实时限额，[Stripe 用量上报](https://docs.stripe.com/billing/subscriptions/usage-based/recording-usage-api) 是异步事件处理，发票/汇总可能滞后，不能作为实时余额来源。

结算与待上报事件原子持久化；使用稳定结算事件 ID、支付幂等键和本地唯一约束防重复。支付接口重试保留原事件身份，在上报拒绝、迟到或发票已结清时进入纠正/对账流程，不能静默丢失或挪到下一期。不能仅依赖厂商有限的去重窗口实现永久幂等。

webhook 按 [Stripe 官方要求](https://docs.stripe.com/webhooks) 用原始请求体、签名与 endpoint secret 验签，检查时效并区分测试/生产环境；验签后可靠持久化接收记录再快速回应。按 event ID 去重，必要时按业务对象与事件类型再去重。事件可乱序，处理时核对支付对象当前状态、账号与租户映射，不相信浏览器跳转成功、客户端金额或单个未经验证的回调。积压或账本不可用时拒绝新的付费执行，免费状态查询尽量保持可用。

| 情况 | 建议费用与恢复规则，正式上线前须确认 |
| --- | --- |
| 输入非法、权益不足、用户拒绝、报价过期，未派发 | 不扣额度；不启动 worker |
| 确认未启动的排队取消 | 释放预留，无任务扣费 |
| 固定任务成功，交付条件与验证范围达到 | 扣约定额度并释放剩余预留 |
| 服务故障且未交付约定结果 | 建议返还任务额度；保留实际内部成本，不要求用户承担未披露的故障重试 |
| 用户代码缺依赖、测试失败或结果部分完成 | 报价前披露哪些是收费诊断交付、哪些是失败；规则缺失时不默认收满额度 |
| 执行后用户取消 | 等停止与用量/副作用证据后结算；固定任务和用量模式分别约定，不自动全扣或全退 |
| 超时/断线/结算未知 | 冻结并对账；不把超时当免费重试依据 |
| 订阅支付失败、撤销或争议 | 暂停新增付费工作；已运行任务按原许可处置，不能篡改历史账单或销毁证据 |
| 退款已提交，pending/failed/unknown | 保留原退款身份并查询；只有确认成功才显示已退款，不另建重复退款 |

服务额度返还与现金退款不同。任务失败先按规则恢复服务额度；退订或现金退款单独审批并绑定原 payment/invoice、租户、金额及既有退款，累计不超过可退原款。若先恢复额度又现金退款，须在同一业务流程消除对应权益，避免双重补偿。根据 [Stripe 退款文档](https://docs.stripe.com/refunds)，退款可能 pending 或 failed，失败仍需安排后续处理，不能把 API 接受请求当作到账。

## 7. 项目、执行与凭据安全

### 7.1 工作区与本机路径

云端不能直接访问用户电脑项目路径，更不能开放本地 `register(path)` 让远程用户任意读取服务器文件。最小 SaaS 接收用户明确选择的材料包或有限权限的仓库导入，创建租户作用域的不透明工作区 ID；路径仅在已授权 sandbox 内解析。

导入限制文件类型、体积、文件数和解压后容量，拒绝路径穿越、符号/硬链接逃逸、敏感文件和解压炸弹；URL 导入防 SSRF、私有地址与重定向逃逸。默认不上传全量聊天、凭据或整机配置。工作区/会话/资产/提案/运行/审批的读取、分页、状态与恢复都核对租户和版本，不能只信一个形似合法的 ID。现有按路径计算 ID 的本地登记方式不能直接充当租户隔离。

### 7.2 worker 与用户代码

每个租户任务有独立文件系统、状态目录、SDK 会话、资源预算和可回收执行边界；云端选定的 OS 沙箱必须实际验收，不能直接拿未验证的平台支持当生产保证。

- 默认最小网络权限，拒绝内网、云元数据、宿主文件系统、容器控制 socket 和跨租户资源。
- CPU、内存、进程、磁盘、输出、超时、并发及模型 Token 预算由执行器限制，涵盖 fork bomb、挂起测试与重试。
- 用户测试、工具、安装脚本、仓库说明和模型生成代码均不可信；不在 edge 或账本进程中执行，不自动给部署、发送或外部写入权限。
- 模型凭据仅由可信 runtime/代理持有，用户代码不得取得原始 Key；必要出网通过限定端点/请求范围的代理，不能成为可转售的通用模型网关。
- 生成提案与应用分离。云端 apply 只能写获批的云端工作区；传回本地后由用户 Coding Agent 审阅并应用，重新检查本地版本。云端验证不代表本地环境或生产验证。

本地连接器、自动同步项目、部署 Agent、企业私网和常驻 worker 均不是第一阶段要求；若未来引入，另评估授权与数据传输，不为复用本机路径而绕过边界。

### 7.3 账号与模型商业授权

本机沿用个人 runtime 登录态只是当前本地使用方式，不能直接搬到多租户收费服务共享。商业运行拟采用运营主体合法持有的 API 项目/组织凭据，或合同明确授权的其他方式；凭据放在服务端受控密钥系统，按租户成本和预算核算，不返回用户、不写 Skill/提示词/工具结果。

[OpenAI Services Agreement](https://openai.com/policies/services-agreement/) 第 2.2 条允许 API 集成到客户应用提供给终端用户，第 3.1/3.3 条限制共享或转售账号访问及转让 API Key；这不是对当前个人套餐、第三方路由或所有 Codex 托管模式的自动授权。上线前须核对实际供应商、账号合同、SDK 运行与 API 认证方式、模型可用地区和成本。默认不提供 BYOK；如以后需要，另评估安全凭据交接，禁止在插件聊天中索取 Key、密码或验证码。

## 8. 数据保留、隐私与许可证

上线前发布与实现一致的数据合同，明确谁处理哪些数据、流向、模型供应商与子处理商、存储地区、访问权限、是否用于训练/改进及用户的导出和删除渠道。不能把传输加密称为端到端加密；worker 和模型处理代码所需明文应如实披露。

| 数据 | 建议保留边界，具体期限待地区与用户确认 |
| --- | --- |
| 原始材料、临时 sandbox | 任务所需最短期限；结束或到期自动清理；用户可请求提前删除 |
| 提案、结果、脱敏运行证据 | 支持用户读取/导出和约定争议窗口；到期删除或匿名化 |
| unknown 运行与争议证据 | 为对账有限保留；披露例外与处理渠道，解除后执行正常清理 |
| 财务/权益账本与必要审计 | 按适用法定与合同期限保留最小必要字段，避免保存完整源码 |
| token、原始 API Key、支付卡信息 | 不进入模型上下文、普通日志或任务资产；短期凭据独立管理、轮换和撤销 |

清理覆盖对象存储、状态、索引、缓存、日志和备份生命周期，提供删除回执；不能承诺当前尚不存在的自动删除能力。运维访问需最小权限、审计和受控临时授权，遥测与成本统计提前披露，不默认为收集全聊天或跨租户训练素材。

项目尚未选许可证，须明确源码发行、托管服务和生成产物授权，不能写成已获 MIT 等许可。核验 SDK/runtime、MCP/其他依赖、打包 Skill/参考资料、模板及导入用户代码的许可证、再分发/商用条件和署名义务；公共可读不等于可自由复制收费。用户应保证提交代码与材料有处理授权，生成代码仍需要依赖、版权与安全检查。

## 9. 外部销售与宿主政策

自营 MCP 收费可行性与客户端内销售许可分开判断。依据本轮读取的 [OpenAI Plugin guidelines](https://developers.openai.com/plugins/plugin-guidelines)，截至 2026-11-09，插件可让用户登录既有付费账号使用已包含权益；不得在插件内销售数字订阅/credits、发起订阅、推销升级或直接链接结账/购买流程。可客观说明权益不足，不能把提示做成间接付费升级漏斗。

因此建议独立官网/合同完成商业关系，插件只提供既有权益访问；消费确认用于执行已授权服务，不做数字产品购买。面向该渠道是否允许扣任务额度的具体体验仍须提交审核核验，不能凭通用 MCP 规范承诺准入。其他宿主以及 Codex 本地插件单独核对各自规则，不把 ChatGPT 插件条款扩展成所有 MCP 客户端的统一政策，也不为该渠道额外加价。

### 10.1 失败矩阵

以下必须由测试或实际回执证明，文档自检和 mock 不能替代真实远程/支付/沙箱验收。

| 探针 | 必须观察到的结果 |
| --- | --- |
| 无 token、过期、错误 issuer/audience/resource、撤销权限 | 拒绝访问/执行，不泄露其他租户记录；在实际采用的 token 类型下核验对应签名与状态 |
| 猜测他人 workspace/session/run/proposal/asset、复用审批 | 调用、读取、分页、恢复、应用均拒绝；请求中的 tenant 字段不能覆盖认证身份 |
| cached tool 或直接调用受限 operation | 执行时权益检查生效，不因工具可见而放行 |
| 报价过期，材料/operation/目标版本变化 | 原报价或批准失效，不重定价后静默执行 |
| 同键多次提交、不同会话竞争余额、同键不同请求 | 一份预留/逻辑任务/结算，冲突可见，余额不负 |
| reserve 后/派发后/settle 前崩溃，队列重复投递 | 恢复同一任务；旧 worker 被 fencing；不重复模型工作或副作用 |
| 接收超时但实际执行完成，付款/退款请求超时 | 保持 unknown 冻结并对账，不释放再扣、不新增付款/退款 |
| fake/replayed/乱序 webhook、支付厂商 429/5xx、事件汇总滞后 | 验签、去重、可靠重试/对账；额度与消费不由异步汇总决定 |
| 已付任务 verify 失败、服务故障、取消、退款失败 | 按原规则分别展示结果与账务状态；不误报通过/已退款，不双重补偿 |
| 恶意代码、穿越/链接、SSRF、fork bomb、输出洪泛 | 资源/网络/路径限制真实拒绝；没有模型/支付/他租户凭据泄露 |
| 无人类确认通道，模型伪造 approve | 消费与文件写入停在需确认；不能通过另一入口绕过 |
| 删除/导出请求、备份恢复、unknown 长期冻结 | 期限及回执可核对，恢复不使已删除数据重新可见；有人工升级和最小争议保留 |

### 10.2 压测与运行放量条件

- 先冻结明确 operation、材料大小、模型和验证配置，再测单任务成本/延迟；公开样本及覆盖，不能把小样本成功率推广成生产可靠性。
- 使用多租户并发提交、同租户竞争最后额度、频繁免费轮询、队列积压和 worker/账本/支付故障注入，比较执行与读接口的隔离性。
- 记录吞吐、p50/p95/p99、队列深度、每任务成本、预留/实扣一致性、unknown 数量与存续时间、结算/webhook 积压、拒绝与取消确认率；阈值在压测前按确认的容量冻结，未测不写达标。
- 必须保持余额不负、重复任务无重复账单、越权/密钥泄露为零的测试不变量；账本/沙箱失效时 fail closed，停止新付费任务，保留免费读取和对账路径。
- 本地 MCP 回归、真实云端目标 OS/宿主验收、支付测试环境及真实有限交易分别报告。版本升级需重测关键边界，不能用前一版本验收替代。
